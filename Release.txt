DC++ Experimental release process
====================

This document describes the steps involved in producing a DC++ Experimental release:

1) Requirements
2) Docs & locale
3) Version update
4) Changelog update
5) Tag the repository
6) Distro build (in 2 steps)
7) Check and rename the files
8) Upload the files
9) Testing -> Stable status


1) Requirements
---------------

Refer to the ``Compile.txt`` file for requirements.

2) Docs & locale
----------------

Copy updated help folder and all translation templates and translations (contents of /po folders) from DC++.

3) Version update
-----------------

Update version numbers in:

- ``dcpp/version.h``

- ``win32/DCPlusPlus.rc``


4) Changelog update
-------------------

Set the first line of the ``changelog.txt`` file to refer to the new version. Example::

    -- 0.851 2015-04-06 --


5) Tag the repository
---------------------

Tag the repository according to the version number. Example::

    git tag 0.860


6) Distro build 
---------------

Ensure your repo is clean (no ``.sconsign.dblite`` file; no ``build`` directory) and
also that all the files required but cannot be added to the repo are all present 
(e.g. HTMLHelp includes and libs) then:

- Build the distribution:

    scons distro=1


7) Check and rename the files
-----------------------------

The ``build/distro`` directory should contain 3 files; check their contents:

- ``DCPlusPlus-xxx.exe``: 64-bit installer. Ensure it runs fine.

- ``DCPlusPlus-xxx-x64.zip``: 64-bit binary arche. Should contain 8 regular files and a ``locale``
  directory with 5 files per language.

- ``DCPlusPlus-xxx-src.zip``: Source code. Should be a direct extract of the DC++ repository.

**Don't forget to replace the "xxx" parts of the file names with the actual version number.**


8) Upload the files
-------------------

- Upload these 3 files to the GitHub project.

- Make a pass on their details once they are uploaded to indicate what they are, etc. 


9) Update version_exp.xml
-------------------------

If you opt to a testing distribution first then you can add / uncomment the <Testingxx> parts
of the ``version_exp.xml`` file stored by the web site to start offering the testing release 
for a small subset of the userbase first.
If no testing period needed, go on...


10) Testing -> Stable status
----------------------------

After some time or when you consider the released version stable:

- Update the ``version_exp.xml`` file stored by the web site with the new stable version number.
  Also remove / uncomment the <Testingxx> parts of the file until / unless there's a new version
  marked as ``Testing``.
